# Little Spark

An illustrated Arduino workbench for a child's first electronics project. Seven animated steps lead from meeting a Uno R3 or R4 WiFi to wiring and blinking a real LED.

## Home page and gear store

`/` introduces the project with a parallax circuit illustration, a scrolling parts/build/test walkthrough, an interactive blink-delay preview, family account explanations, and FAQs. Gear Store beside Sign in opens https://littlespark.vtc.store in a new tab. The shirt drawing is an illustration, not a product listing. Motion respects reduced-motion preferences; mobile layouts use a static illustration.

The lesson workspace is at `/learn/`. Home-page sign-in opens `/signin/`. The server checks the session before serving `/learn/`; parent and child accounts can enter. Parent and child magic links continue to open the lab, and existing browser progress keys are unchanged. The app tour covers Home, the lab, and the gear link. Vite builds the home, sign-in, and lab entry points; Vercel rewrites magic-link routes to the sign-in entry point. The lab bundle is loaded only after a session check.

## How-to and family profiles

The public [How-to guide](https://littlespark.tech/how-to/) walks through parent email sign-in, child profiles, one-use five-minute links/QR codes, opening the correct learner profile, the Starter Kit checklist, camera/layout controls, the guided editor, virtual testing, parent progress monitoring, and optional Uno upload. It is available from the home page, sign-in page, and lab. The lab opens it in a separate tab.

A link’s five-minute expiry limits when it can be redeemed; it does not limit lesson duration. Browser tabs share sign-in, so use the child’s device or a separate browser profile to keep the parent dashboard signed in. Reopen Family to refresh progress. Continuing on another device uses a new link for the same child profile. Revoking a child’s sessions preserves their profile and progress.

`AGENTS.md` requires the How-to and in-app tour to change with affected user workflows, and the home page to change with major features. The owner has confirmed parent email sign-in, child profile creation, child login, and progress appearing in Family on production.

## What works

- Original procedural Three.js Uno R3, breadboard, LED, 220 Ω resistor, and jumper wires.
- Seven guided steps, animated part placement, replay, component inspection, cursor-anchored zoom, rotation, pan, and touch pinch zoom.
- Three guided Blink rhythms (250 / 500 / 1000 ms) and virtual LED colors.
- Real AVR8js execution of compiled Arduino firmware in a Web Worker. The test checks six D13 transitions and their timing.
- SHA-256 checks for the firmware artifacts. Upload uses the exact byte image that passed emulation.
- Desktop Web Serial connection and STK500v1 upload for Uno R3 or R4 WiFi / ATmega328P / Optiboot at 115200 baud. Verifies chip signature before writing and reads flash back after writing.
- Parent practice is browser-local; child progress syncs to an account. No analytics or external compilation service.

## Real board

Use a **Uno R3 or R4 WiFi**, USB cable, breadboard, standard 5 mm LED, 220 Ω resistor, and two jumper wires. Uno R4 Minima, Nano, ESP32, and other bootloaders are not supported by this lesson.

With USB unplugged, place the LED across the center gap: long leg E11, short leg F11. Resistor C11–C17, D13–A17, GND–J11. Letters correspond to the five connected holes on each side of the center gap; check your breadboard's numbering and orientation.

Pass the virtual test in step 7, open **Connect a board**, have an adult check the board and wiring, connect using a browser with Web Serial (desktop Chrome/Edge), and select **Send tested code**. Serial access requires HTTPS or localhost and a user gesture. The test validates program behavior; it cannot validate physical wiring. R4 WiFi upload and running-flash verification were tested on a physical board; the owner confirmed its built-in light and breadboard LED blink. R3 remains covered by protocol tests; new physical builds still require a wiring check.

Firmware is constrained to supplied, precompiled lesson variants. The displayed sketch matches the source of each artifact. This is not an arbitrary-code compiler or a general analog circuit simulator.

## Firmware and verification

Checked-in `.hex`, `.ino` and SHA-256 manifest files are generated by `scripts/build-firmware.mjs`. To rebuild, install Arduino CLI and `arduino:avr@1.8.8` plus `arduino:renesas_uno@1.6.0`, then run:

```sh
node scripts/build-firmware.mjs
npm test
npm run build
```

The GitHub Actions workflow compiles fresh firmware on Ubuntu, tests the output, builds the app, and retains the verified firmware as a downloadable artifact. On Apple Silicon, Arduino's official AVR toolchain may need Rosetta; CI avoids that host dependency.

## Controls

Drag to rotate and tilt. Choose **Move**, Shift-drag, right-drag, or middle-drag to pan. Scroll or pinch to zoom. Touch: one finger rotates, two fingers pan and pinch. Q/E turn; up/down arrows tilt; WASD pan; +/− zoom; R resets. Buttons offer the same camera functions. Click a component, chip, port, or pin header to animate into its detail; **Back to this step** or Escape returns to the previous diagram. Close-ups keep the circuit connected and the model visible. A compact floating field-note card uses a dotted leader and a marker to identify the selected component; its close button also returns to the diagram. Connection and parent guides open as non-blocking floating panels. Reduced-motion preferences disable camera easing.

## App tour and guided editor

**App tour** in the header and **Learn your way around** in the field guide open a separate practice lesson covering navigation, rotation/tilt, pan/zoom, detail inspection and return, code, testing, USB upload, workspace layouts, family accounts, and saved progress. Floating Back/Next controls stay available while exploring the actual interface. Practice does not complete circuit steps or change the saved checklist; the previous blink settings are restored on exit. USB connection and upload are never automatic.

The guided code editor edits both wait instructions with **Blink delay** (250 / 500 / 1000 ms). It is intentionally not a free-text compiler. Changes invalidate the old emulator result. Copy code exports the matching sketch to the clipboard.

`AGENTS.md` requires tutorial updates in the same change as every new, removed, or changed user-facing feature. UI regions declare `data-tour-feature`; tests verify every declared feature is covered by `src/app-tour.js` and every tutorial target exists. Camera help lives in `src/view-controls.js`.

## Rendering stability

Camera easing is time-based and snaps to its exact destination below a subpixel threshold. Idle views do not redraw, and shadow maps are cached until a component moves or scene visibility changes. Edge lines do not write depth; shaded faces and outline shells use separate depth offsets to avoid flicker during zoom. LED simulation invalidates the frame whenever its output changes.

## Workspace and accounts

Choose **Build + Code**, **Build only**, **Code only**, or **Guided** above the workbench. Build + Code displays both panes side by side on wider screens and stacks them on narrow screens. The lesson controls stay available below the panes. Guided uses a wider instruction panel on screens above 1100px. Its content scrolls independently with scroll chaining contained; the workbench height stays fixed while reading. Keyboard users can focus the instruction region and scroll it. New steps and layout changes reset its scroll position. At 1100px and below, Guided stacks the panels with normal page scrolling. Layout preference is browser-local.

Parents sign in with a single-use email link. The parent dashboard can create and rename child profiles, view step completion, generate a five-minute child login link/QR code, and revoke child sessions. Kids do not provide email addresses or passwords. Links use friendly words plus a random suffix, are stored as hashes, and are consumed atomically. Signed-in child progress is stored in Neon Postgres; parent practice stays on the device. Progress resets invalidate stale writes from other devices. Account changes in another tab block stale saves and show a persistent message with Reload. Locally recovered progress is sent back to the server after sign-in.

Backend setup: copy `.env.example` to `.env.local`, supply server credentials, and run `node --env-file=.env.local scripts/migrate.mjs`. Production uses Vercel Functions, Neon, and Resend. Sender-domain DNS must be verified before email sign-in works. Never put production credentials in PR preview deployments.

Run `node --env-file=.env.local scripts/check-accounts.mjs` for database integration checks. It creates temporary test families and removes them afterward; it does not send email.

## Sparky’s guided code help

Ask Sparky** in the notebook opens nonmodal, lesson-specific help with the selected goggles hedgehog artwork. **Give me a hint** highlights both `delay()` lines. **Show a faster blink** / **Show a slower blink** previews the next supported timing; **Try it** applies it through the same verified-firmware invalidation path as the timing control. **Undo Sparky’s change** restores the prior timing and also requires a fresh test. ## Makey Makey 101 — Fruit Piano

`/learn/makey-makey/` is a sign-in-protected second lesson, reachable from both lab field guides and the homepage. Seven steps cover a kit/home checklist, USB, EARTH, a direct SPACE experiment, three fruit inputs, and playing C/D/E. Supplies: Makey Makey Classic, supplied USB data cable (adapter if needed), four alligator leads, three bananas or foil pads, computer and dry surface. Original SVG diagrams animate connections, highlight the closed path, support zoom/pan/reset and part inspection; reduced motion removes animation. This is a connection visualization, not an electronics emulator or a new Arduino firmware target.

In step 7 choose **Virtual practice**, connect virtual EARTH and tap the keys, or **Real board / keyboard**, **Sound on**, then **Focus piano**. Space/Left/Up play C/D/E through Web Audio; Mute preserves visual feedback. Keyboard shortcuts are captured only while the piano region itself has focus, ignore repeats and never capture form typing. Makey Makey acts as a USB keyboard, with no Web Serial or upload flow; this works through ordinary browser keyboard input, including Safari. Keyboard input does not identify the board or prove wiring correctness. A physical Makey Makey has not been hands-on tested here. Wiring follows the [official first-time guide](https://makeymakey.com/blogs/how-to-instructions/first-time-set-up-basic-how-to-guide).

Progress uses the existing per-kid/lesson schema with the allowlisted `fruit-piano` ID. Blink keeps `first-circuit` and its existing storage keys; no data migration is needed. Each lesson has independent generations, reset/merge semantics and client storage. Family shows both seven-step progress rows. Switching lessons flushes pending saves first. The Makey-specific tour lives in `MAKEY_TOUR_STEPS` in `src/app-tour.js`; its coverage tests include all declared UI regions. ## Arduino lesson 3 — Traffic Lights

`/learn/traffic-lights/` reuses the Arduino app shell, original procedural workbench, camera/inspection, four layouts, Sparky, exact-firmware USB uploader and family controls. `src/arduino-lessons.js` holds the shared Arduino content plus Traffic Lights steps, connection data and the sketch generator used by both browser exports and compilation. This is a first shared built-in lesson structure, not a public drop-in loader.

The seven steps use one Uno R3, USB cable, breadboard, red/yellow/green LEDs, three 220 Ω resistors and six jumpers. LED columns are 4/13/22 across E/F; resistors connect C4–C10, C13–C19, C22–C28; signals D13–A10, D12–A19, D11–A28; common return GND–H4, J4–J13, I13–J22. These fit the same 30-column breadboard geometry. USB stays unplugged during wiring.

`trafficSource(unit)` generates explicit HIGH/LOW and delay instructions for red → green → yellow. Red and green each last `2*unit`, yellow `unit`, with 250/500/1000 ms units. The firmware builder compiles all six Blink/Traffic variants with the pinned Uno core and publishes SHA256 records. `verifyTraffic` runs actual AVR instructions, checks seven phase starts, order, timings and rejects overlapping active outputs; the worker then streams the actual three-bit port state to the model. The uploader can send only the verified image, invalidated on any pace change or Undo. Download/clipboard sketch matches the compiled source. Physical Uno uploads remain unvalidated by a hands-on test.

Traffic progress uses the `traffic-lights` allowlisted lesson ID, independent local keys/generation/reset. Family shows all six 7-step lesson rows and an overall count out of 42. Existing Blink and Fruit Piano saves remain separate. Both Arduino routes use lesson-aware App tour content; home cards/FAQ and How-to section 12 document wiring, pace, Sparky and upload. The later Conductivity Detective and Game Controller lessons extend the Makey Makey track.

## Six-lesson progression and shared catalog

`src/lesson-catalog.js` is the single allowlist for lesson IDs, navigation and Family summaries. There are three Arduino lessons (Blink, Traffic Lights, Push-button Light) and three Makey Makey lessons (Fruit Piano, Conductivity Detective, Game Controller). All live below the sign-in-protected `/learn/` prefix and save independently. The home page has six lesson cards; public How-to sections 13–15 and the matching app tours cover the new workflows.

**Conductivity Detective** (`/learn/conductivity/`) uses a two-lead SPACE/EARTH tester with foil, banana, dry plastic and dry wood. Predictions and observed key/no-key results are stored with an explicit virtual/real mode. Prepared virtual examples are not material measurements. Real observations are user-recorded keyboard events or the **Record no key** action; a missing key may be a setup/contact issue. Four experiments finish the lesson regardless of prediction accuracy. The API validates four known sample IDs and finite record fields; keyed records merge across saves, with per-lesson reset generations preventing stale resurrection.

**Game Controller** (`/learn/game-controller/`) uses four foil arrow pads and EARTH, five leads total. Spark Hunt moves one square per distinct arrow press on a bounded 5×5 board. Three sparks complete the lesson; there is no timer. Virtual moves require EARTH, real moves require the activity region to be focused. Position and collected spark IDs save to the child profile. **New round** preserves completed lesson progress; a lesson reset clears the round too. Both new Makey lessons share `makey-activities.js`, data, diagrams and the eight-step activity tour, with prepared Sparky explanations, part notes, replay, zoom/pan/reset and reduced-motion support.

**Push-button Light** (`/learn/button-light/`) shares the Arduino shell and original 3D geometry. LED E11/F11, 220 Ω C11–C17, D13–A17, GND–J11. Four-leg button E22/F22/E24/F24: each column is an always-connected pair, pressing joins the pairs. D2–A22 and J24–I11 add the input and return. Check switch orientation with a grown-up. INPUT_PULLUP means released HIGH, pressed LOW, following the [official Arduino example](https://docs.arduino.cc/built-in-examples/digital/InputPullupSerial/). Two compiled rules implement press=on/off. The verifier injects released/pressed/released on the emulated D2 input; interactive virtual presses then drive that same input. Sparky previews the output rule and Undo invalidates verification. The exact verified image remains the only upload source. The firmware builder now compiles eight positive variants total. Physical kits still need hands-on validation.

## Choosing a 220 Ω resistor

All three Arduino lessons share an inline, collapsible **Find the 220 Ω resistor** guide during unboxing and resistor placement, plus **Read the color bands** from resistor inspection. Four-band red/red/brown/gold and five-band red/red/black/black/brown examples show magnified bands, written color names, the 22×10 / 220×1 calculation and separated tolerance band. Body color/size can differ; other tolerance colors are possible. The guide asks a grown-up to check the kit label or measure a loose, unpowered part if uncertain. It does not identify a physical resistor, change firmware or complete checklist steps. The public How-to uses the same interactive component at `/how-to/#find-resistor`; all Arduino App tours cover it. Home’s parts explanation and kit FAQ link it. No new account data is collected.

## Uno R4 WiFi

Choose the board in Connect a board. Its procedural model includes USB-C, RA4M1, ESP32-S3, Qwiic and the 12 × 8 LED matrix. The chosen board persists locally; USB VID/PID detection selects R4 WiFi automatically and invalidates prior firmware verification. R4 Minima is not supported.

The pinned Renesas core is `arduino:renesas_uno@1.6.0`. `scripts/build-r4-firmware.mjs` compiles all eight lesson variants and records binary SHA256, source SHA256 and ELF symbols. `src/r4-simulator.js` executes actual setup/loop Thumb instructions; digital I/O and delay calls are modeled. Unsupported instructions/calls and invalid stacks fail closed. This is bounded sketch execution, not full RA4 peripheral/startup emulation. The worker remains separate from AVR8js.

`src/r4-uploader.js` uses the official SAM-BA ASCII extension after a 1200-baud touch, stages 4096-byte blocks and writes only sketch offsets beginning at physical `0x4000`. Some factory bootloaders advertise Z but time out, also with Arduino bossac verification. Instead the running sketch answers an explicit `LS?` host query with CRC32 computed directly over the full flashed binary, including its core and patched image-length field. Only a match with the exact simulated image reports success. CRC32 detects transfer corruption; it is not cryptographic device authentication. The source helper is in `scripts/r4-attestation.h`, is modeled as host-only I/O in simulation and leaves the lesson pin behavior unchanged. No bootloader or ESP firmware is replaced.

R4 core is MIT with bundled components retaining their licenses, including LGPL-2.1 Arduino API. Corresponding core/variant source and notices are supplied under `public/firmware/licenses/ArduinoCore-renesas-1.6.0-source.tar.gz`; upstream: https://github.com/arduino/ArduinoCore-renesas/tree/1.6.0. Bootloader protocol reference: https://github.com/arduino/arduino-renesas-bootloader. Build requires the pinned AVR and Renesas cores. Public guide `/how-to/#choose-board`, home and app tour describe board choice, verification and recovery.

Hardware validation (2026-10-28): the shared browser uploader ran through a Web Serial-compatible native transport against the owner’s connected R4 WiFi. Flash attestation matched and the owner confirmed both the orange L indicator and breadboard LED blinked after correcting component positions. Browser UI simulation/board switching are tested separately; physical serial chooser behavior still depends on the browser.
